# CLAUDE.md

eBike Manager is a self-hosted app for Bosch eBike Flow riders. It signs in to Bosch the way the Flow app does, syncs rides on a cron schedule, keeps a backup of every ride's FIT file, shows the rides in a Blazor dashboard, and uploads them to Google Health through an integration. It is built with .NET 10, Blazor Interactive Server, MudBlazor 9 with the vendored Modernity CSS patch, EF Core (SQLite) and the Garmin FIT SDK.

The code follows the owner's other project, Speedtest Watcher (`E:\Projects\Myspeed\dotnet`, see its CLAUDE.md). When something here isn't covered, do what Speedtest Watcher does.

## Commands

Run these from this folder, which contains `EBikeManager.slnx`.

```bash
dotnet build
dotnet test
dotnet test --project tests/EBikeManager.UnitTests
dotnet test --project tests/EBikeManager.IntegrationTests --filter-not-trait "Category=Browser"
dotnet test --project tests/EBikeManager.IntegrationTests --filter-trait "Category=Browser"
pwsh tests/EBikeManager.IntegrationTests/bin/Debug/net10.0/playwright.ps1 install chromium
dotnet run --project src/EBikeManager.Web
dotnet ef migrations add <Name> --project src/EBikeManager.Application --startup-project src/EBikeManager.Web --output-dir Data/Migrations
docker compose up -d --build
```

A running app (Visual Studio or `dotnet run`) locks the build output. Build and test into a scratch folder instead by passing the same `--artifacts-path <folder>` to `dotnet build` and `dotnet test` (with `--no-build`).

| Environment variable | Effect |
| --- | --- |
| `PORT` | Listening port (default `2004`). |
| `DATA_DIRECTORY` | Folder for the database, data-protection keys and FIT archive (default `data` in the working directory, `/app/data` in Docker). |
| `DISABLE_AUTH=true` | Turns sign-in off (recovery from broken OIDC settings). |

These are hosting settings only. Everything else is configured in the UI and stored in the database; don't add environment variables for app behaviour. All three are read into `EBikeManagerOptions` by `EBikeManagerOptionsSetup`.

## Architecture

| Project | Contents |
| --- | --- |
| `src/EBikeManager.Application` | Everything the app does. No ASP.NET Core. |
| `src/EBikeManager.Web` | The website. `Program.cs` only composes the installers and middleware. |
| `tests/EBikeManager.UnitTests` | Fakes only: no database, files, host or browser. |
| `tests/EBikeManager.IntegrationTests` | SQLite, temporary files, the real host and Playwright. |
| `tests/EBikeManager.TestSupport` | Shared test helpers: `FakeBoschApi`, `FakeBoschAuth`, `FakeGoogleHealthApi`, `FakeGoogleHealthAuth`, `FakeEsphomeBridge` (a localhost ESPHome API device, plain or encrypted, single or dual), `BoschSamples` (real-shaped JSON and an embedded PNG bike picture), `TestFit`, `RecordingHandler` (records headers too), `FixedAccess`, and for notifications `TestNotifications`, `InMemoryNotificationChannels`, `FixedSettings`, `FixedTime` and `Approvals`. |

Classes go in the folder of their kind, never a feature folder: `Services/` (+ `Interfaces/`), `Repositories/` (+ `Interfaces/`), `BackgroundServices/`, `Handlers/`, `Exceptions/`, `Models/` (`Entities/`, `Dtos/`), `Enums/`, `Configuration/`, `Installers/`, `Utils/`, `Data/` (`Converters/`, `Migrations/`), `Resources/`. The website adds `Controllers/`, `Services/` (circuit state and access), `Utils/`, `Resources/` and `Ui/` (`Layout/`, `Pages/`, `Pages/Settings/`, `Controls/`).

Services, models and the interfaces services take are `public`. The DbContext, repositories, HTTP clients (`BoschApiService`, `BoschAuthService`, `GoogleHealthApiService`, `GoogleHealthAuthService`), the authentication handlers and background services are `internal`. `ArchitectureTests` enforces the rules Speedtest Watcher has: Web references only Application, Application has no ASP.NET Core, only repositories/`Data`/installers touch the DbContext, types using `HttpClient` are internal, components never inject repositories, unit tests open no database or host.

### Bosch eBike Flow

- **Sign-in** copies the ha-bosch-ebike-flow Home Assistant integration: Keycloak at `p9.authz.bosch.com`, client `one-bike-app`, redirect `onebikeapp-ios://…/oauth2redirect`, scope `openid offline_access`, PKCE, `kc_idp_hint=skid`. The redirect only reaches the Flow app, so the user copies it from the browser's Network tab and pastes it into `BoschSignIn`. `PkceLoginService` keeps each pending login's verifier keyed by `state`; the code expires after about a minute.
- **Tokens:** `BoschConnectionService` (singleton) caches the access token and stores the refresh token encrypted through `SecretStoreService` (`secrets` table, protected by `ISecretProtectionService`, which the Web implements with Data Protection). A rotated refresh token is saved at once. `invalid_grant` becomes `BoschReauthRequiredException` and the status `ReauthRequired`. `BoschAuthenticationHandler` adds the bearer token and retries once after a 401.
- **Endpoints** (`BoschEndpoints`): bikes from `obc-rider-profile…/v1/bike-profile`, rides from `obc-rider-activity…/v1/activity?page=&size=&sort=-startTime`, FIT files from `…/v1/activity/{id}/export/fit`. `startTime` is epoch seconds (milliseconds are accepted too). Distance is metres, `durationWithoutStops` seconds, `averageSpeed` km/h.
- **Bike details** come from `obc-rider-profile…/v2/bike-profile/{id}`, `…/v1/state-of-charge/{id}` (ConnectModule only, 404 otherwise), `bike-pass…/v1/bike-passes`, `theft-detection…/v0/latest-locations?bikeId=` and `in-app-purchase…/v1/subscription/status`. Only the profile is required. Read them with `JsonElementExtensions` and turn them into `BikeDetailsDto` with `BikeProfileParser`. The profile names assist modes only by ID (`A100M40010`…), so names and colours come from recent rides' `assistModeUsage`. `mediaAssets.bike_picture_url` is snake_case. Each assist mode's `statistics` holds its lifetime `distance` (metres) and `consumedEnergy` (Wh); together they add up to `totalDistanceTraveled`, and the mode `0` is riding with the motor off. The Bikes page shows each mode's Wh per km or mile once it has a kilometre (`AssistModeMileageDto.WattHoursPerKilometre`). `driveUnit.tuningDetection` has `isDetected` and `counter`. The state of charge has `stateOfChargeLatestUpdate` (ISO) and `remainingChargingTime` (minutes, while charging). The bike pass has `frameNumber`, `frameNumberPosition` (free text such as "Seat stem") and `files` (`BIKE_IMAGE`, `BIKE_INVOICE`, `LOCK_INVOICE`; the same `fileId` can be listed twice with different `updatedAt`). Without a ConnectModule the cloud has no battery charge level (`batteryLevel`/`remainingEnergy` are null); the Flow app reads it over Bluetooth. The cloud also doesn't have what the Flow app reads from the bike over Bluetooth: wired and Bluetooth components (eShift, Mini Remote, other paired devices; `bleComponents` stays empty) and whether a software update is available (release management's `bikes/{id}/update-sets` needs the drive unit's application versions, which the profile leaves `null`). Don't build either from cloud data.
- **FIT files** from Bosch have no calories, and their `local_timestamp` equals UTC, so ride times use Bosch's `timeZoneOfActivity`. Records come in interleaved streams at the same timestamps (GPS-only records; speed/power/cadence/altitude records several times a second). Calories always come from Bosch's summary (`caloriesBurnt`), which accounts for the motor; that is also the figure to export.

### Sync

`SyncSchedulerService` waits for the next `syncCron` occurrence (hourly by default, evaluated in UTC), restarts its wait when `syncCron` changes, and calls `SyncRunService.RunScheduledAsync`, which does nothing until setup is complete. `SyncStateService` is the only run lock and publishes every status change through `IAppEventService.SyncStatusChanged`. Manual syncs (`StartManualSyncAsync`) check access, take the lock, and run in their own scope until the app stops.

`RideSyncService` reads Bosch's ride list newest first. The first sync, or one after the bike selection changed (`boschFullScan`), reads every page; later ones stop at the first page with no new rides and nothing from the last 7 days. It then downloads each missing FIT file, checks it with `FitDecoder`, and saves it through `FitArchiveService` as `fit/yyyy/MM/yyyy-MM-dd_HHmm_{id}.fit` (ride-local time) with Bosch's summary JSON beside it. A 404 marks the ride `FitUnavailable`; other failures are retried on the next sync. The ride's GPX file (`…/export/gpx`, `Accept: application/xml`) is downloaded the same way and saved as is beside the FIT file (`GpxPathFor`, same name with `.gpx`), separately from the FIT so either can fail alone; a 404 marks `GpxUnavailable`. It is only checked to contain `<gpx` (`GpxFile.LooksLikeGpx`) and never parsed. Bosch's GPX has only `trkpt` lat/lon (5 decimals), `ele` and `time`; no speed, cadence, power, distance or heart rate.

Bosch's cloud has no bike name or model name (the Flow app keeps the user's name on the phone and in the bike's Bluetooth name). A bike's `model` is Bosch's "Brand (Drive unit)" from `BoschJson.BikeName`: it can't be edited, `SaveSelectionAsync` refreshes it, and it is what Google Health gets as the device and in the notes. Its `name` starts as the model and is the user's own (Settings → Bike names, `BikeService.SaveNamesAsync`); everything in eBike Manager shows the name, and the model only on the Bikes page, the ride page and to tell apart bikes with the same name (`BikeText.WithModel`, `BikeText.Labels`). Each ride keeps both (`rides.bikeName`, `rides.bikeModel`): the sync sets them and `RenameBikeAsync` keeps them current while the bike is chosen, so a ride still shows its bike after that bike is unticked; read them from the ride, never by looking the bike up. With more than one bike, the Bikes page has a tab per bike and the Rides list a bike filter and the bike under each date, both kept in `?bike={id}` (`BikeLinks`), and the dashboard's one bike card flips between bikes (`BikeCarousel`, arrows and a dot per bike; MudCarousel needs a fixed height) with its Bike details link opening the shown bike's tab.

`BikeDetailsSyncService` runs after the rides (and from the Bikes page's Refresh). It stores each bike's raw JSON on the `bikes` row and downloads the bike picture once per picture URL through the `bosch-media` client, which sends no Bosch token. The picture is kept only if `ImageFormat` recognises it as PNG, JPEG, GIF or WebP. It lives in `bikePictures` and is served by `BikesController` at `bikes/{id}/picture?v={ticks}`. The bike pass files are downloaded with the Bosch token from `bike-pass…/v1/files/{bikeId}/{fileId}` (built from the IDs, never from the pass's `link`) when new or when their `updatedAt` changed, kept only if `DocumentFormat` recognises an image or PDF of at most 25 MB, and stored in `bikeDocuments`; files gone from the pass are deleted. They are served at `bikes/{id}/documents/{fileId}?v={ticks}` (`BikeMediaEndpoint`).

### Ride details and maps

`RideService.GetDetailAsync` reads the ride's FIT backup with `FitDecoder.ReadRecords` and builds the page data with `RideTrackBuilder`. Bosch records a value only when it changes, so records are merged per second and every value carries forward until it changes. The route keeps every distinct position (thinned to 4,000), and `RouteValues` gives each kept point its speed, power, cadence, gradient and heart rate, with speed and heart rate averaged over ±2 s, power and cadence over ±5 s, and the gradient taken over the surrounding 100 m. The chart series is bucketed by distance (at most 1,000 points). Splits are timed while moving: an interval counts when the distance grew within 30 s. They average cadence and power over pedalling only (non-zero values), like Bosch's own averages. A split is a kilometre or a mile, by the units (`GetDetailAsync` takes the `UnitSystem`). `RideDetailParser` adds Bosch's summary (top speed, cadence, power, CO₂, `assistModeUsage` in metres, and `brakeEvents.amountOfAbsInterventionEvents`, which only bikes with ABS have).

The map and charts are drawn by `wwwroot/js/ebike-manager-maps.js` (`window.ebikeManagerMaps`), called through `MapViewService`. It loads the vendored MapLibre GL JS 5.24.0 and uPlot 1.6.32 from `wwwroot/lib` on first use. Chart colours come from the MudBlazor CSS variables. Pages re-theme the map and charts through the `DarkMode` cascading value from `MainLayout` (`AppTheme.DarkModeCascade`). The map source comes from the `mapProvider`, `mapStyleUrl` and `mapDarkStyleUrl` settings (`MapSettings`, turned into a `MapSource` by `MapSources`):
- OpenStreetMap raster tiles, inverted with raster paint in the dark theme
- OpenFreeMap `liberty`/`dark`
- the user's own MapLibre style

The ride page can colour the route by speed, power, cadence, gradient or heart rate (`RouteColours`; only the values the ride has, speed by default, the last choice kept in local storage as `routeColour`):
- **Colours:** a blue, cyan, green, yellow, orange, red ramp on a fixed scale per value (`RouteColours.Scales`: speed 0–35 km/h or 0–22 mph, power 0–300 W, cadence 0–100 rpm, gradient −10 to +10 %, heart rate 60–180 bpm), so a colour means the same on every ride; values beyond the ends take the end colour. Absolute elevation has no fixed scale that works everywhere, so the route offers the gradient instead. Neighbouring colours are at least 16 apart (OKLab ΔE×100) for normal vision and 12 under colour-blindness simulations, over a near-black casing in both themes so every colour keeps at least 4.6:1 contrast. A legend in the map's bottom-left corner names the value, its unit and the scale.
- **Drawing:** each route step is its own short line with its values, in a GeoJSON source with `tolerance: 0`, because MapLibre otherwise drops lines shorter than its simplification tolerance. Switching colour only changes the paint (`ebikeManagerMaps.setColour`). The ride map fits the route inside a padding that keeps it clear of the colour picker and the legend.

The Display tab's map preview draws the route of the newest of the last 10 rides that has one (`RideService.GetLatestRouteAsync`), or `SampleRoute`, about 2 km along the Victoria Embankment in London, when none has.

### Units

The `units` setting (`metric` or `imperial`, read as `AppSettings.Units` through `UnitSettings`) changes only what pages show. Bosch data, the database, the DTOs, `/api/statistics` and Google Health stay metric (metres, km and km/h). Imperial is miles, mph and feet; `UnitConversion` holds the factors and the unit labels.
- **Showing values:** `MainLayout` cascades the unit system (`DisplayFormat.UnitsCascade`). Format distances, speeds and heights with the `DisplayFormat` methods that take a `UnitSystem` (`Distance`, `WholeDistance`, `DistanceNumber`, `Speed`, `SpeedNumber`, `ShortDistance`), never by dividing by 1,000 in a page. Charts get their labels and factors from `ChartUnits`, and the ride page reloads when the units change, for its splits.
- **Choosing:** the Display tab (`SettingsDisplay`, units above the map settings) and the welcome wizard's first step, which suggests imperial for `en-US` and `en-GB` browsers (`UnitSettings.SuggestFor`).

### eBike bridge

The live battery level and other bike values come from Xunil99's Bosch eBike LDI bridge, which users flash from `BridgeSettings.SetupUrl` (https://xunil99.github.io/ha-bosch-ebike/; source `github.com/Xunil99/ha-bosch-ebike`, `esphome/factory.yaml` and `factory-dual.yaml`). Name it as that bridge and link to that page, not as an example of ESPHome bridges. It's read over ESPHome's native API on TCP 6053. No Home Assistant: `EsphomeConnection` speaks the plaintext framing (`0x00`, varint length, varint type) or, with the optional key, Noise_NNpsk0_25519_ChaChaPoly_SHA256 (`NoiseHandshake`, `NoiseCipher`; prologue `NoiseAPIInit\0\0`; X25519 from BouncyCastle, the rest from .NET), with hand-written protobuf (`ProtoReader`, `ProtoWriter`, `EsphomeMessages`, `EsphomeMessageType` from ESPHome's `api.proto`). The Noise code is tested against the published test vector and `FakeEsphomeBridge` (TestSupport) was checked against aioesphomeapi, plain and encrypted.
- **Running:** `BridgeListenerService` loads `bridgeAddress`, `bridgeFirstBike`, `bridgeSecondBike` and the secret `bridgeEncryptionKey`, runs a `BridgeSession` (Hello, an empty AuthenticationRequest like Home Assistant, DeviceInfo, ListEntities, SubscribeStates; it answers Ping, GetTime and Disconnect, pings every 20 s and gives up after 90 s of silence) and retries from `FirstRetry` (5 s) doubling to 5 minutes. `BridgeService.SaveAsync` publishes `BridgeSettingsChanged`, which restarts it at once. Failures become `BridgeStatus.Problem` from `ApplicationStrings` (needs key, not encrypted, wrong key, unreachable, no answer).
- **Sensors:** `BridgeSensors.Find` matches entity names after `eBike ` (dual: `eBike 1 `/`eBike 2 `, slots 1 and 2); anything else is ignored. "System Locked" arrives inverted (the bridge sends on for unlocked, for Home Assistant's lock class), so `Locked = !state`. The bridge has no bike identity, so the user maps each slot to a bike; a single bridge with one saved bike maps itself, and the Bridge tab warns when a slot's odometer is below the chosen bike's Bosch odometer.
- **Kept and shown:** only the battery percentage and the odometer are stored, with their time, on the `bikes` row (`bridgeBatteryPercent`, `bridgeOdometerKm`; the odometer at most once a minute and when the bike disconnects). `BikeProfileParser` makes `OdometerMeters` the higher of Bosch's and the bridge's (`BoschOdometerMeters` keeps Bosch's own). Every other value lives only in `BridgeStateService` and is shown only while that slot reports Connected (`BridgeSnapshot.LiveFor`); pages get changes through `IAppEventService.BridgeChanged` and `BridgeLiveStateService`.

### Local only

Pages are built from local data. The eBike bridge is on the user's network and is contacted by `BridgeListenerService` whenever an address is set. Bosch is contacted only by syncs, the Bikes page's Refresh, sign-in, and `BikeChooser`'s Refresh bikes. `BikeChooser` starts from the saved bikes and reads the account's bikes by itself only when none are saved (the welcome wizard); Google only by syncs and the Google Health settings tab's connect and disconnect. The OIDC provider is contacted by the server when sign-in is saved and while someone signs in, and by the browser only to sign in. Notification services are contacted by the server at the end of a sync, for the webhook keep-alive, and by Send test. Never put a Bosch or other third-party URL in rendered HTML: download media during the sync and serve it from the app. Fonts are vendored in `wwwroot/fonts` (`css/fonts.css`) and scripts in `wwwroot/lib`. The only outside requests a page may make are the map tiles and style from the map server the user chose. Browser tests answer those locally, and any other outside request fails the test.

### Integrations

An integration implements `IRideIntegration` (`Key`, `DisplayName`, `GetExportWindowAsync`, `ExportAsync`) and is registered as a scoped `IRideIntegration`.
- **When it runs:** `IntegrationSyncService` runs as the last step of every sync. For each integration with an export window (connected and configured), it takes up to 100 finished rides from the window that have no `Uploaded` row in `rideExports` for that integration, oldest first.
- **Per ride:** each ride's outcome is saved as a `RideExport` (status, remote ID, note, problem, attempts).
- **Single rides:** `IntegrationSyncService.ExportOneAsync(key, rideId)` uploads one finished ride regardless of the export window. The Rides list and ride page call it through `GoogleHealthAccountService.UploadRideAsync`, via the shared `GoogleHealthUploadButton` control. The Rides list is the only per-ride list of uploads (the Google Health tab shows counts only); its icon and the ride page's `UploadStatusChip` take their colour from `UploadAppearance`: green uploaded, amber uploaded with a note, red failed. It is refused with `Conflict` while a sync is running, so the two never upload the same ride at once.
- **Failures:** an `HttpRequestException` fails one ride, and it's retried on the next sync. Three failures in a row stop that integration's run. `IntegrationSignInRequiredException` stops the integration and becomes a sync problem without marking rides failed.

**Google Health** (`GoogleHealthIntegration`, `GoogleHealthAccountService`, `GoogleHealthConnectionService`, `GoogleHealthApiService`):
- **Sign-in:** the user creates a *Web application* OAuth client in their own Google Cloud project. Connecting requires eBike Manager to be opened over HTTPS on a domain (a reverse proxy), or on `localhost`, which the browser tests use; `GoogleHealthRedirect.IsAllowed` checks this. The Google Health tab (`SettingsGoogleHealth`, `/settings/google-health`) builds the redirect URI from `NavigationManager.BaseUri` plus `GoogleHealthCallback.Path` and shows it for the user to register. `StartSignInAsync` saves the client ID, client secret and upload choice, then starts a PKCE login that carries the redirect URI, and the page navigates to Google in the same tab. `GoogleHealthController` (`/integrations/google-health/callback`) calls `CompleteSignInAsync` and redirects to `/settings/google-health?googleHealth=connected|failed`. The callback path stays under `/integrations/` because users registered it with Google. The reason for a failure is kept in `GoogleHealthConnectionService` for the page to show, never put in the URL. Scopes are `openid email` plus `googlehealth.activity_and_fitness` `.writeonly` and `.readonly`. The client ID is a setting; the client secret and refresh token are secrets. The app stays in Testing with the user as its only test user, as in the owner's ha-googlehealthscalesync integration, which keeps its sign-in without renewing; don't tell users to publish it.
- **Upload:** only `exercise` can be written. `GoogleHealthExercise` turns a ride into an `ELECTRIC_BIKE` exercise with Bosch's `caloriesKcal`, and `GoogleHealthJson` builds the JSON. The data point ID is `ebike-{rideId}` (4–63 characters of `a-z0-9-`). After every create, `GoogleHealthApiService` reads the data point back (up to three GETs, a second apart). A ride only counts as uploaded when Google returns it; a 409 or operation error 6 counts only if the read-back finds it, otherwise the upload fails with Google's message. Google's create answer is logged at Information.
- **Watch rides:** before uploading, `ListWatchExercisesAsync` reads `google-wearables` exercises by civil start time (the filter only supports civil time for sessions), from two hours before the ride to its end. `WatchRides` keeps bike exercises (`BIKING`, `OUTDOOR_BIKE`, `MOUNTAIN_BIKE`, `ELECTRIC_BIKE`) that overlap at least half of the shorter of the two. Such a ride is not uploaded: it gets the status `WatchRecorded` (shown as Failed) with the reason as its problem, eBike Manager's own earlier `ebike-{rideId}` upload is removed (`RemoveOwnExerciseAsync`), and the sync doesn't retry it; the single-ride upload re-checks. Tested with the owner's real account: a ride uploaded next to a watch ride never shows in Fitbit, Google refuses to delete or change data it didn't get from this app, and a deleted watch ride leaves data behind in Health Connect. So don't add ways to replace, update or delete watch rides; the Google Health tab tells Fitbit and Pixel Watch users to turn off automatic recognition of bike rides instead.
- **Upload choice:** `googleHealthUploadFrom` is `all` or a UTC instant (`yyyy-MM-ddTHH:mm:ssZ`).

### Notifications

Copied from Speedtest Watcher's integrations, under eBike Manager's names (it calls ride uploads integrations). Each notification type is one class in `Services/Notifications/` implementing `INotificationTypeService` (`Name`, a `Schema` the settings form is built from, `HandleAsync` returning `Sent`, `NotApplicable` or `Failed(reason)`, and `SendTestAsync`). Register every type in `AddNotifications()` (`NotificationInstaller`); the order is the Add notification menu's. Discord, Telegram, Gotify, ntfy, Pushover and Apprise derive from `MessageNotificationService`, which handles the per-event toggles (`send_*`), the editable `*_message` templates with `%name%` placeholders (`TemplateVariables`, culture-invariant, in the `units` setting; `TemplateHelper` adds `%year%` to `%second%`) and the defaults in `MessageTemplates`; it skips events a channel doesn't send before checking its settings, so a broken channel isn't marked failed by every keep-alive. The webhook posts `{ "event": "RIDE_SYNCED", "data": … }` (metric, from `NotificationEventData`) and the optional keep-alive. `HttpNotificationService.SendAsync` uses the `notifications` HTTP client and turns errors and non-success answers into `Failed` with a readable reason.
- **Events** (`Models/Events/`) are published by `SyncRunService` after `SyncStateService.Finish`, never during a sync, through `INotificationDispatchService`, which records each channel's last run (`notificationChannels.lastActivity`, `activityFailed`) only when it sends or fails:
  - `RideSynced`: rides that became finished in a sync that isn't a full scan (`SyncRunResult.FinishedRideIds`), so the first import and a rescan stay quiet.
  - `UploadFailed`: a ride's first failed upload only (`RideExport.Attempts == 1`; `IntegrationRunResult.FailedUploads`), not watch-recorded rides.
  - `SignInRequired`: Bosch (`BoschReauthRequiredException`) or an integration (`IntegrationRunResult.SignInsRequired`), once until the service is signed in again (`NotificationStateService.SignedIn`, called by the account services).
  - `SyncFailed` and `SyncRestored`: only when sync goes from working to failing and back, so an outage sends one message. A Bosch sign-in problem isn't a failed sync.
  - `Heartbeat`: every minute from `NotificationTickerService`, for the webhook keep-alive, throttled per channel by `HeartbeatScheduleService`.
  `NotificationStateService` keeps these edges in memory, so a restart may repeat one.
- **Settings:** the Notifications tab (`SettingsNotifications`) is Speedtest Watcher's integrations page: a panel per channel with its name, the schema's fields (labels and placeholders in `NotificationText`), Save, Send test (the newest finished ride, or `NotificationService.SampleRide`; it ignores the toggles and saves nothing) and Delete. `NotificationService` checks access and the settings against the schema (`NotificationSettingsRules`). Icons are in `wwwroot/img/notifications`, from Dashboard Icons, mapped in `NotificationIcons`.
- **Tests:** `NotificationRequestTests` records every request each type sends for every event and for Send test in `NotificationRequests.approved.txt`, and every settings form in `NotificationSchemas.approved.json`. After a deliberate change, run the tests with `EBIKE_MANAGER_APPROVE=1` and review the diff. Every `TestApp` answers the `notifications` client with `TestApp.Notifications`, a `RecordingHandler`.

### Settings and access

Settings are key/value rows in the `config` table, defined in `SettingDefinitions` and read as the typed `AppSettings`. Save through `SettingsService` (or `SettingsStateService` in the UI) so `SettingsChanged` follows. Sign-in keys are saved only by `SignInService`.

Sign-in is optional and uses the owner's own OpenID Connect provider, as in Speedtest Watcher but without its read-only visitors, and with an API token that opens only the statistics endpoint: when it is on, nothing else is shown to anyone who isn't signed in.
- **Settings:** `authEnabled`, `oidcAuthority`, `oidcClientId`, `oidcScopes` (always starting with `openid`) and `authStamp` are Security-tab settings (`SignInSettings`); the client secret is the secret `oidcClientSecret`. `SignInService.SaveAsync` checks the provider's discovery document first (`IOidcDiscoveryService`), starts a new `authStamp` when sign-in is turned on or the provider or client changes, then calls `AuthSettingsService.ReloadAsync`, which caches an `AuthSnapshot` and adds or removes the OIDC scheme at runtime. The retired `authPasswordHash` key is deleted at startup (`SettingDefinitions.ObsoleteKeys`).
- **Signing in:** `OidcOptionsSetup` configures the code flow with PKCE, query response mode, the userinfo endpoint and no saved tokens, and adds the current stamp to the cookie as `signInStamp` when the token is validated. `AccessPolicy.Decide` grants full access when sign-in is off or the cookie's stamp matches, so changing the provider signs everyone out. The callback is `/signin-oidc`; failures go to `/auth/failed`, which names `DISABLE_AUTH`.
- **Enforcing it:** the fallback authorization policy (`FullAccessRequirement`) covers every endpoint without `[AllowAnonymous]`, including the pages, `/_blazor` and the controllers. `AccessDeniedResponder` answers `/api`, `/_blazor` and the media under `/bikes/…` with a 401 (switching status-code pages off, or `/not-found` would redirect instead; `/api` adds `WWW-Authenticate: Bearer`) and redirects everything else to `/auth/login?returnUrl=…`, which starts the challenge. A circuit that loses access (sign-in just turned on, or the provider changed) is sent there by `MainLayout`. Only `AuthController`, the health check and the static files (`MapStaticAssets().AllowAnonymous()`) are anonymous.
- **API token and statistics:** `GET /api/statistics` (`StatisticsController`, `StatisticsService`, `StatisticsDto`: bikes, rides, `mileageKm`, `movingTimeSeconds`, `elevationGainMeters`, `caloriesKcal` from the all-time ride totals) has the `AccessPolicies.Statistics` policy instead of the fallback: `StatisticsAccessRequirementHandler` grants it on full access or a bearer token (`BearerToken`) matching `AuthSnapshot.ApiTokenHash`. No other handler looks at bearer tokens, so the token opens nothing else; keep it that way, and keep `StatisticsService` free of access checks, because a token request has no full access. The token (`ebm_…`, `ApiToken`) is the secret `apiToken`, encrypted like the others so the Security tab can show it. `SignInService.GetApiTokenAsync` creates it the first time it's asked for while sign-in is on, `RegenerateApiTokenAsync` replaces it, and both reload `AuthSettingsService`, which caches only its SHA-256 hash. Changing the provider keeps the token.
- **Signing out** is a form POST to `/auth/logout` with an antiforgery token, checked in the action with `IAntiforgery` (the app has no MVC view services, so `[ValidateAntiForgeryToken]` can't work). It shows `/auth/signed-out` while sign-in is on, because `/` would sign straight back in through the provider. The two `/auth` pages are plain HTML from `AuthPage`, styled by the `em-auth-` classes.

`MainLayout` sends the owner to `/welcome` until setup is complete. Services that change data start with an access check.

## Conventions

The Speedtest Watcher conventions apply, including:

- No comments of any kind (vendored `modernity.patch.css`, EF `.Designer.cs` files and the model snapshot are exempt).
- Constructor injection into readonly fields, file-scoped namespaces, one type per file, `_camelCase` private fields.
- UI text in `Web/Resources/WebStrings.resx`; service messages in `Application/Resources/ApplicationStrings.resx`. Fill placeholders with `WebStrings.Format` / `ApplicationStrings.Format`. Units stay in code.
- Fallible service methods return `OperationResult`/`OperationResult<T>`; show `result.Message ?? fallback`.
- Log through `[LoggerMessage]` partial methods. Catch specific exceptions.
- Warnings are errors and the recommended analyzers run. Package versions live in `Directory.Packages.props`.
- In Razor, a `string` component parameter needs `@` to pass a field (`ErrorMessage="@_error"`); without it Blazor passes the literal text.
- Custom CSS goes in `wwwroot/css/ebike-manager.css` with `em-` classes. `App.razor` links styles and scripts through `@Assets["…"]`, which `MapStaticAssets` turns into content-hashed names, so an upgrade never pairs new pages with an old cached file (`StaticAssetTests`). Files asked for by their plain name (the map libraries, the `/auth` pages' stylesheet) are sent as `no-cache` and checked again on every load. Timestamps are stored in UTC (`UtcDateTimeConverter`); the UI shows ride times in the ride's own time zone and everything else in the browser's (`PreferencesService`).
- A new migration: run `dotnet format style EBikeManager.slnx --diagnostics IDE0005 IDE0161 --severity warn`, then delete its `#nullable disable` and `/// <inheritdoc />` lines.

## Tests

- xUnit v3 and FakeItEasy on Microsoft.Testing.Platform. Test names are PascalCase sentences. Pass `TestContext.Current.CancellationToken` to every call that takes one.
- Integration tests use `TestDatabase` (in-memory SQLite, `EnsureCreated`) and `TestApp` (`WebApplicationFactory` with its own temporary `DATA_DIRECTORY`, no background services, `FakeBoschApi`/`FakeBoschAuth`, and no network). `NotSetUpApp`, `SetUpApp`, `SignInRequiredApp` and `SignInSwitchedOffApp` (sign-in saved but `DISABLE_AUTH=true`) seed it through `SampleData`. `FakeOidcProvider` is the OIDC provider every `TestApp` uses: it answers the discovery check and the handler's backchannel (discovery, keys, token with PKCE and client secret checks, userinfo) and signs real ID tokens. Its authorization endpoint is served by the test host itself (`FakeOidcSignInPage`, a startup filter), because a browser can't be intercepted on a redirect from `/auth/login`.
- Browser tests (`Browser/`) use `BrowserApp` on a free Kestrel port. Map tiles and styles are answered with a blank tile and style. Full-page screenshots lose the WebGL map, so `RideDetailTests` saves a tall viewport capture (`ride-detail-hover.png`) for the README. Give each class `[Collection(BrowserTestGroup.Name)]` and `[Trait("Category", "Browser")]`, find elements by role, label or text, and end with `AssertNoBrowserErrors()`. `PageLayoutTests` saves every page in both themes at 1280px and 390px to `bin/Debug/net10.0/TestResults/browser`; look at them after UI changes. Set `EBIKE_MANAGER_BROWSER_TESTS=required` to fail instead of skipping when Chromium is missing.
- Tests never reach Bosch or any other real service.
